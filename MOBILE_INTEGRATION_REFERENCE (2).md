# Mobile Integration Reference — StartupET

Generated by static analysis of the repository at commit `07367eb` (branch `invigorate`). This document is a reference for building a Flutter/Capacitor (or any native) mobile client against the existing Next.js 15 App Router API. It does not reflect any code changes — it is a snapshot of what exists today, including known gaps and inconsistencies that a mobile client will need to work around.

Where a shape could not be determined precisely from source (no Zod schema, no explicit type), this is stated explicitly rather than guessed.

## 1. Authentication

### 1.1 Provider & session mechanism

- **Library**: `next-auth@^4.24.10`, configured in `lib/auth.ts`.
- **Provider**: `CredentialsProvider` only (email + password). No OAuth providers are registered in NextAuth itself. There is a separate, parallel **Fayda (Ethiopian National ID) OIDC flow** used for identity verification (`app/api/auth/callback/fayda/route.ts`, `NEXT_PUBLIC_FAYDA_*` env vars) — this is *not* a NextAuth provider; the OIDC token exchange happens client-side in the browser, and the callback route is a redirect-only fallback. It does not currently create or attach a NextAuth session.
- **Session strategy**: `jwt` (`session.strategy: "jwt"`), `maxAge: 3 days` (`3 * 24 * 60 * 60` seconds).
- **Session cookie**: Not explicitly configured (no `cookies` block in `authOptions`), so NextAuth's defaults apply:
  - `next-auth.session-token` over HTTP, or `__Secure-next-auth.session-token` when served over HTTPS in production.
  - `httpOnly: true`, `sameSite: lax`, `secure` (true in production).
  - Related cookies: `next-auth.csrf-token` (`__Host-next-auth.csrf-token` on HTTPS) and `next-auth.callback-url`.
- **CSRF**: Handled by NextAuth's built-in double-submit cookie pattern via `GET /api/auth/csrf`. Only relevant to the NextAuth `signIn`/`signOut`/`callback` form-post endpoints — plain `fetch`-based API routes elsewhere do not appear to check a CSRF token themselves.
- **Login/logout/session endpoints** (all handled by the single NextAuth catch-all at `app/api/auth/[...nextauth]/route.ts`, exporting `GET`/`POST` that delegate entirely to `NextAuth(authOptions)`):
  - `POST /api/auth/callback/credentials` — actual login (credentials exchange). Requires a valid CSRF token obtained from `GET /api/auth/csrf` first (standard NextAuth flow).
  - `GET /api/auth/session` — returns the current session JSON (or `{}` if unauthenticated).
  - `POST /api/auth/signout` — clears the session cookie (also requires CSRF token).
  - `GET /api/auth/csrf` — issues the CSRF token/cookie pair.
  - `GET /api/auth/providers` — lists configured providers (would show `credentials` only).
- **`authorize()` behavior** (`lib/auth.ts`), relevant for a mobile login screen's error handling:
  - Rate-limited: `rateLimit(`login:${email}`, 5, 900)` — 5 attempts / 15 minutes per email (DB-backed, fails open on DB error).
  - Throws (surfaced as NextAuth `CredentialsSignin` error, message preserved): `"Email and password required"`, `"Too many failed login attempts. Please try again in 15 minutes."`, `"Invalid email or password"` (user missing / no password set, or bad password), `"Your account has been suspended. Please contact the administrator."`, `"Account temporarily locked due to too many failed login attempts. Please try again later."`, `"Email not verified. Please check your inbox."` (unless role is `SUPER_ADMIN`).
  - On success, resets `loginAttempts`/`lockedUntil`, records a `UserSession` row (`token: crypto.randomUUID()`, `isActive: true`) that becomes the session's `sessionToken` claim (see `GET/POST /api/auth/sessions` below — lets a user list/revoke active sessions/devices).
  - Writes an `AuditLog` row (`action: "USER_LOGIN"`) via `signIn` callback.
- **JWT/session claims** (`types/next-auth.d.ts`, `lib/auth.ts` callbacks): `id`, `role` (raw `UserRole` string), `permissions` (flattened array of permission codes from all assigned `Role`s), `stakeholderId`, `firstName`, `lastName`, `address`, `phoneNumber`, `image`, `twoStepAuthEnabled`, plus internal-only JWT fields `sessionToken`, `lastVerified`, `revoked`.
- **Live revalidation**: every JWT refresh re-checks the DB at most once per 60 seconds (`SESSION_REVALIDATE_INTERVAL_MS`) — if the user is suspended, soft-deleted, or their `UserSession` row was deactivated (see `POST /api/auth/sessions` "terminate"), the token is marked `revoked` and the `session` callback returns `{ ...session, user: undefined }`, i.e. an authenticated-looking response with no `user` — **a client must treat "no `user` key" as logged-out, not just "no session"**.

### 1.2 Why this doesn't work for a fully-native app, as-is

The credentials login flow is a **cookie + CSRF-token web flow**, not a bearer-token API:

1. It requires first fetching a CSRF token/cookie (`GET /api/auth/csrf`), then POSTing credentials plus that token to `/api/auth/callback/credentials`, and the server responds by **setting an httpOnly cookie** — a native HTTP client (Dart `http`/`dio`, etc.) can technically replay this dance (cookie jar + form POST), but it's brittle, undocumented as a stable contract, and NextAuth does not treat it as a versioned public API.
2. All subsequent API routes read the session via `getServerSession(authOptions)`, which extracts the JWT **from the cookie** — there is no `Authorization: Bearer <token>` support anywhere in this codebase. A native app has no cookie jar shared with a browser and no standard way to persist/send this cookie securely across app restarts the way a mobile keychain-backed bearer token would work.
3. There is no refresh-token / token-refresh endpoint — the JWT simply lives 3 days in the cookie and is silently revalidated server-side; there's no client-facing "refresh" contract to build against.

**A WebView-wrapped app is the exception**: if the mobile shell is a WebView (Capacitor, or a thin native WebView wrapper) sharing a persistent cookie store with the embedded browser context, the existing cookie session works unmodified — login via the normal web form, and the WebView's cookie jar carries the session to subsequent API calls made from JS inside that WebView (or even from native code if the cookie store is shared, e.g. `CookieManager` on Android / `WKWebsiteDataStore` on iOS). This requires no backend changes.

### 1.3 Proposed bearer-token endpoints (do not exist yet — must be added for a fully-native client)

None of the following exist in the codebase today. They are proposed additions, shaped to slot alongside the existing `authOptions`/Prisma models with minimal new schema:

| Endpoint | Method | Purpose | Proposed request | Proposed response |
|---|---|---|---|---|
| `/api/mobile/auth/login` | POST | Exchange credentials for a bearer access + refresh token pair | `{ "email": string, "password": string, "deviceId"?: string, "deviceName"?: string }` | `{ "accessToken": string, "refreshToken": string, "expiresIn": 900, "user": { "id", "role", "firstName", "lastName", "email" } }` |
| `/api/mobile/auth/refresh` | POST | Exchange a refresh token for a new access token | `{ "refreshToken": string }` | `{ "accessToken": string, "expiresIn": 900 }` |
| `/api/mobile/auth/logout` | POST | Revoke a refresh token / device session | `{ "refreshToken": string }` (bearer access token in `Authorization` header) | `{ "success": true }` |

Implementation notes for whoever builds this: the existing `UserSession` model (`prisma/schema/user.prisma`) already tracks `token`/`isActive`/`userAgent`/`ipAddress` per login and is checked during JWT revalidation (`lib/auth.ts`) — it is a natural place to also store a hashed refresh token and device metadata, so revoking a device via the existing `POST /api/auth/sessions` `"terminate"` action could double as mobile-session revocation if the two systems are unified. Rate limiting should reuse `lib/rate-limit.ts`'s `rateLimit()` helper (already used for the credentials login and OTP-style verification endpoints).

### 1.4 Identity verification (Fayda National ID) — not full login

- `NEXT_PUBLIC_FAYDA_*` env vars configure an OIDC client for Ethiopia's Fayda national ID system, used for **identity verification during application submission**, not as an authentication method. The actual token exchange happens client-side (browser OIDC library); `GET /api/auth/callback/fayda` is a bare redirect fallback (no code exchange, no session creation, no DB writes) — see endpoint inventory.
- Separately, authenticated users can verify a National ID number against Fayda via `GET /api/verify-national-id?fcn=<16-digit-number>` (server-to-server call to the Fayda platform, requires `FAYDA_API_KEY`/`FAYDA_ACCESS_TOKEN` server env vars — returns `501` if unconfigured).

## 2. Authorization / Roles

### 2.1 Role enum (`UserRole`, `prisma/schema/user.prisma`)

| Role | Portal / dashboard | Mobile-relevant? |
|---|---|---|
| `USER` | `/dashboard/home` — default startup-founder role | **Yes** — primary mobile persona (applicant/startup founder) |
| `ECOSYSTEM_BUILDER` | `/ecosystem-builder` | **Yes** — secondary mobile persona (incubator/accelerator/investor-adjacent org) |
| `SUPER_ADMIN` | `/super-admin` | Unlikely on mobile, but has universal bypass on every role gate |
| `ADMIN` | `/admins-new` | Web-portal-oriented, not a mobile target |
| `REGIONAL_ADMIN` | `/regional-admin` | Web-portal-oriented |
| `HUB_MANAGER` | `/hub-portal` | Web-portal-oriented |
| `MENTOR` | `/mentor-portal` | Web-portal-oriented |
| `COMMITTEE` | `/committee-portal/dashboard` | Web-portal-oriented |
| `REVIEWER` | `/committee-portal/dashboard` | Web-portal-oriented |
| `STAKEHOLDER` | `/stakeholder` | Web-portal-oriented |

For a v1 mobile app, **`USER`** (startup founders tracking their application/certificate/funding/events) and **`ECOSYSTEM_BUILDER`** (incubators managing their own applications/spaces/funding opportunities) are the two roles worth targeting.

### 2.2 `middleware.ts` route-prefix → role mapping

`middleware.ts` wraps `next-auth/middleware`'s `withAuth`. Its `authorized` callback requires a non-revoked JWT (`!!token && !token.revoked`) for **every matched path** before the inner `middleware()` function even runs; failing that returns NextAuth's own redirect/401. The inner function then enforces:

| Path prefix (page + `/api/...` twin) | Allowed roles | On API-path violation |
|---|---|---|
| `/admins-new`, `/api/admins-new` | `ADMIN`, `SUPER_ADMIN` | `403 {"error":"Unauthorized"}` |
| `/committee-portal`, `/api/committee-portal` | `COMMITTEE`, `REVIEWER`, `SUPER_ADMIN` | `403 {"error":"Unauthorized"}` |
| `/ecosystem-builder`, `/api/ecosystem-builder` | `ECOSYSTEM_BUILDER`, `SUPER_ADMIN` | `403 {"error":"Unauthorized"}` |
| `/super-admin`, `/api/super-admin` | `SUPER_ADMIN` | `403 {"error":"Unauthorized"}` |
| `/stakeholder`, `/api/stakeholder` | `STAKEHOLDER`, `SUPER_ADMIN` | `403 {"error":"Unauthorized"}` |
| `/regional-admin`, `/api/regional-admin` | `REGIONAL_ADMIN`, `SUPER_ADMIN` | `403 {"error":"Unauthorized"}` |
| `/hub-portal`, `/api/hub-portal` | `HUB_MANAGER`, `SUPER_ADMIN` | `403 {"error":"Unauthorized"}` |
| `/mentor-portal`, `/api/mentor-portal` | `MENTOR`, `SUPER_ADMIN` | `403 {"error":"Unauthorized"}` |
| `/dashboard` (page only, no `/api` twin) | `USER` (else redirected to role's dashboard, except `/dashboard/*/messages` which is shared) | n/a (not an API path) |
| `/api/protected` | any authenticated, non-revoked JWT | `403` implied via `authorized` callback |

**Critically for the endpoint inventory below**: the `config.matcher` list is **exhaustive** — only the prefixes above are touched by middleware at all. Every other `/api/**` route (applications, certificates, startups, files, events, funding, notifications, pitches, verify-*, cron, audit-log, hub-reports, reports/submit, auth/sessions) receives **no middleware protection whatsoever** and must — and, per the extraction below, inconsistently does — perform its own `getServerSession(authOptions)` check and role/ownership logic inline.

## 4. Real-time (notifications)

- **Transport**: Server-Sent Events (SSE), `GET /api/notifications/stream`, `Content-Type: text/event-stream`. Confirmed via manual `ReadableStream` construction, `X-Accel-Buffering: no` (disables proxy buffering), and hand-written `event:`/`data:` frames.
- **Auth**: standard session cookie, checked once at connection open (`getServerSession`). No per-event re-auth, no token in the URL.
- **Event types**:
  - `connected` — sent immediately on open: `{"status":"connected"}`.
  - `notification` — relayed when a global `new-notification` event's `userId` matches the connection's user; payload is a `Notification` row shape (`userId, title, message, type, isRead, link, ...`).
  - `new-message` — relayed when `recipientIds` includes the user.
  - `typing` — same recipient filtering, for chat typing indicators.
  - `user-status` — broadcast to **all** connections unfiltered: `{userId, status: "online"|"offline"}`.
  - Heartbeat: a bare SSE comment line (`: heartbeat`) every 10 seconds, to keep the connection alive through proxies/load balancers.
- **⚠ Important architectural caveat**: the event bus is an in-process Node `EventEmitter` singleton (`lib/event-emitter.ts`), **not backed by Redis or any pub/sub**. In a multi-instance/serverless deployment, an event emitted on one server instance is invisible to a client connected to a different instance. Do not treat SSE delivery as guaranteed — pair it with a periodic REST poll or app-foreground refresh as a fallback.

### 4.1 Mobile consumption pattern

- **Foregrounded**: connect to the SSE stream directly (most native HTTP clients need a dedicated SSE/EventSource-compatible library, since Dart's `http` package doesn't parse SSE framing natively — e.g. `flutter_client_sse` or a raw chunked-response reader). Reconnect on drop with backoff; the stream has no `Last-Event-ID`/resume support, so a reconnect should be followed by a REST fetch of any notifications missed during the gap.
- **Backgrounded**: SSE connections don't survive OS-level app suspension on iOS/Android. Background delivery requires **push notifications (FCM/APNs)**, which do not exist in this codebase today. A device-token registration endpoint would need to be added, e.g.:

| Endpoint (proposed) | Method | Purpose | Request | Response |
|---|---|---|---|---|
| `/api/mobile/devices` | POST | Register/update an FCM/APNs device token for the current user | `{ "token": string, "platform": "ios"|"android", "appVersion"?: string }` | `{ "success": true }` |
| `/api/mobile/devices/:token` | DELETE | Unregister a device token (logout/uninstall) | — | `{ "success": true }` |

  The server-side piece that creates `Notification` rows (`lib/notifications`, referenced by `reports/submit` and others as `notifyAllAdmins`/`createNotification`) would need a corresponding FCM-send call added at the same call sites, keyed off registered device tokens for the target `userId`.

## 5. File handling

There are **two independent upload pipelines** — treat them as unrelated APIs:

### 5.1 `POST /api/files/upload` (the "real" file pipeline, backed by the `File` Prisma model)

- Auth: session required. Rate-limited: 5 uploads / user / 60 seconds (`RateLimit` DB table).
- Request: `multipart/form-data` with fields: `file` (required), `category` (required, upper-cased, must be one of the `FileCategory` enum values below), `metadata` (optional JSON string), `entityType`/`entityId`/`directory` (optional strings), `isPublic` (optional, `"true"` string → boolean).
- **Category → mime/size rules** (`lib/services/file/validators/file-validator.ts`):

  | Category | Max size | Allowed mimes |
  |---|---|---|
  | `BUSINESS_LICENSE`, `ARTICLES_OF_INCORPORATION`, `FINANCIAL_STATEMENT`, `INVESTOR_DOCUMENT`, `TAX_REGISTRATION` | 20 MB | PDF, Word, Excel, PPT, JPEG/PNG/WEBP, CSV, text/plain, RTF, ODT/ODS, ZIP |
  | `PITCH_DECK` | 30 MB | same document mimes as above |
  | `PROFILE_IMAGE` | 5 MB | JPEG, PNG, WEBP |
  | `CERTIFICATE` | 10 MB | PDF, JPEG, PNG, WEBP |
  | `PUBLIC_ASSET` | 50 MB | JPEG, PNG, WEBP |
  | `OTHER` | 20 MB | any mime |

  **⚠ However, an outer pre-check (`lib/upload-limit.ts`) runs first with a flat 10 MB cap** and a separate fixed allow-list (PDF, JPEG/PNG/GIF, DOC/DOCX, XLS/XLSX, CSV, ZIP) — this is *stricter* than several of the per-category limits above and is the effective real ceiling for everything (e.g. a 15 MB `PITCH_DECK` will be rejected by this outer check despite being under its own 30 MB category limit). **A mobile client should assume a hard 10 MB cap on all uploads through this endpoint** until this is reconciled.
- Success: `201` with the created `FileRecord`: `{id, originalName, storedName, mimeType, size, storagePath, storageBucket, uploadedBy, entityType, entityId, category, provider, metadata, isPublic, isDeleted:false, deletedAt:null, createdAt, updatedAt}`.
- **How file IDs get referenced by other resources**: the upload endpoint only returns an `id` — it does **not** write it onto any owning entity. The client must separately PATCH/POST the owning resource with that ID, e.g.:
  - `Application.businessLicenseFileId` / `articlesOfIncorpFileId` / `financialsFileId` / `pitchDeckFileId`
  - `EcosystemBuilder.businessLicenseFileId` / `taxRegistrationFileId` (set via `POST /api/ecosystem-builder/apply`)
  - `News.featuredImageFileId`, `Complaint.fileId`, `FormalRequest.attachmentFileId`, `ApplicationDocumentNote.fileId` (not mobile-relevant endpoints in this set, listed for completeness)
- Errors: `401` unauthenticated; `429` rate-limited; `400` missing file/category or outer-limit validation failure; `409` if the DB `file` schema/table is out of sync (a deployment/migration issue, surfaces to the client as a real error); `500` other failures (including per-category `FileValidationError`s, which are **not** mapped to `400` — they fall through to the generic `500` handler with the validator's message).

### 5.2 `GET /api/files/[id]` / `PATCH` / `DELETE` — metadata & lifecycle

- Auth required; access allowed if `file.isPublic || file.uploadedBy === caller || caller.role in {ADMIN, SUPER_ADMIN}`, else `403`.
- `DELETE` supports `?hard=true` for a real delete (row + storage object); default is soft-delete (`isDeleted:true`).

### 5.3 `GET /api/files/[id]/download` — binary download

- Auth required (session only) — **⚠ no ownership/visibility check at all**, unlike the metadata route above. Any authenticated user who knows/guesses a file `id` can download its bytes. Treat this as a known gap, not a documented ACL boundary.
- Query `?inline=true` for `Content-Disposition: inline` (e.g. rendering a PDF in an in-app viewer) vs. the default `attachment`.
- Side effect: logs a `FileAccessLog` row with `action:"DOWNLOAD"` — attributed to the **file's uploader**, not the requesting user (a logging bug, not a security control).

### 5.4 `POST /api/upload/avatar` — profile picture pipeline (separate from `/api/files/upload`)

- Auth required, no rate limit, no `File` DB row created — writes directly to `public/uploads/avatars/{userId}-{uuid}.{ext}` on local disk.
- 2 MB cap, JPEG/PNG/WEBP/GIF only.
- Returns `{url: "/uploads/avatars/<filename>"}` — the mobile client is responsible for then persisting this URL onto the user's profile (via whatever profile-update endpoint exists — not covered in this route-file set).
- No storage cleanup: repeated uploads accumulate new files under random UUIDs; old avatars are never deleted by this route.

### 5.5 Storage backend

`File.provider` (`StorageProvider` enum: `LOCAL | S3 | VERCEL_BLOB`) — `.env.example` only configures `FILE_STORAGE_PROVIDER=LOCAL` and `FILE_STORAGE_PATH=./storage/uploads`, meaning **the deployed default is local disk storage**, not S3/Blob. A mobile client should not assume file URLs are globally reachable CDN URLs — downloads go through the authenticated `/api/files/[id]/download` proxy endpoint, not a direct storage URL.

## 8. Cross-cutting gaps a native client will hit

Consolidated from the route-by-route extraction above — worth flagging to the backend team before/while building the mobile client, since some of these are security-relevant and others will just cause confusing client-side bugs:

1. **No bearer-token auth exists** — see §1.2/1.3. This is the single biggest blocker for a fully-native (non-WebView) app.
2. **Inconsistent error envelopes** across route families: `{error}` (files, protected, news), `{success:false, error}` (events, funding, ecosystem-builder), plain-text body (SSE 401). A mobile HTTP client layer will need per-family response parsing rather than one shared error type.
3. **Inconsistent role/ownership enforcement** even within a single feature area:
   - `applications`/`applications/[id]` treat `ADMIN|SUPER_ADMIN|REVIEWER` as privileged; `certificates/[id]/download` only treats `ADMIN|SUPER_ADMIN` as privileged.
   - Within `ecosystem-builder`, `application/*`, `apply`, `funding/*`, and `investments/*` enforce real per-builder ownership + certification gates; `bookings/*`, `events/*`, `news/*`, and `spaces/*` rely solely on the middleware role gate and treat those resources as global/shared — any `ECOSYSTEM_BUILDER` can read/write/delete any other builder's bookings, events, attendees, or spaces.
   - Certification-gate logic itself differs: `funding/*` treats a builder as certified if `builder.certified === true` **or** they have any `CERTIFIED` `EcoApplication`; `investments/*` checks `builder.certified` alone.
4. **Two known IDOR-shaped gaps**:
   - `GET /api/events/my-registrations?email=<arbitrary>` — no check that the email belongs to the caller.
   - `GET /api/files/[id]/download` — no ownership/visibility check at all (contrast with `GET /api/files/[id]`, which does check).
5. **`GET /api/events/[id]/register`'s capacity check is dead code** — an event can be over-registered past `capacity` with no error, despite the check being scaffolded in the code.
6. **`GET /api/ecosystem-builder/spaces` has no inline auth check at all** — the only handler in the whole file set that relies purely on the middleware gate with zero route-level session check (functionally fine today since middleware still requires a valid role, but inconsistent with every sibling route).
7. **`POST /api/certificates/generate-pdf` is a pure render endpoint** with no binding to a real `Certificate`/`Application` row — any authenticated user can generate a "certificate" PDF for arbitrary caller-supplied data. Don't expose this as a trusted "download my real certificate" action in the mobile UI — use `GET /api/certificates/[id]/download` for that, which is DB-backed and ownership-checked.
8. **File uploads are effectively capped at 10 MB**, not the higher per-category limits documented in the validator, due to a stricter outer pre-check (§5.1) — a mobile upload UI showing "up to 30MB for pitch decks" (per the `next.config.ts` comment) would be wrong; surface 10 MB as the real limit until reconciled.
9. **SSE notifications are best-effort only** in any multi-instance deployment (§4) — don't build a mobile notification badge that assumes SSE delivery is reliable; poll or refresh on foreground as a backstop, and push notifications (not yet implemented server-side) are required for background delivery.
10. **No REST list/mark-read endpoint for `Notification` was found** among the 50 files reviewed — only the SSE stream. Confirm with the team where notification history/mark-as-read lives (possibly a server action, not a route handler) before building a mobile inbox screen.
11. **`GET /api/funding/[id]` returns the full creator `User` row** (via `include: {creator: true}`) with no field selection — verify this doesn't leak the `password` hash or other sensitive `User` columns into a response a mobile client will parse and potentially log/cache.
